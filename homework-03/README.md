# ДЗ 3: тесты и конкурентность

Эта работа продолжает [ДЗ 2](../homework-02/): gRPC `product-service` на
`:50051` и HTTP-корзину на `:8080`. Контракт protobuf, адреса и формат HTTP-ответа
не менялись.

При чтении корзины сервис теперь запрашивает каждый SKU в `product-service`
отдельной горутиной. У всех запросов общий трёхсекундный таймаут. Результаты
попадают в срез по индексу, поэтому порядок товаров остаётся по возрастанию
SKU, а цены берутся свежие. Если хоть один товар пропал, GET возвращает `412`
без частичного ответа. Пустая корзина не вызывает gRPC. При добавлении товара
исходящий запрос тоже ограничен тремя секундами; HTTP-лог пишет шаблон маршрута,
а не ID пользователя.

Карта корзин уже была защищена `sync.RWMutex` в ДЗ 2. В ДЗ 3 чтение делает
снимок под `RLock` и отпускает его до сетевых запросов; счётчик количества
товара обновляется атомарно. `product-service` читает готовый каталог, который
после загрузки не меняется.

## Проверка

Нужен Go 1.24 или новее. Сгенерированный protobuf уже находится в репозитории;
`protoc` и Go-плагины нужны только для `make generate`.

```bash
cd homework-03
make test         # юнит-тесты; API и race-tag тесты не входят
make test-race    # юнит-тесты + конкурентный тест корзины под race detector
make build
make bench        # BenchmarkGetProduct, BenchmarkAddToCart, BenchmarkGetCart
```

API-тесты ходят в живые сервисы. Откройте второй терминал после запуска
`make run-all`; сами тесты серверы не поднимают:

```bash
# Терминал 1, из homework-03
make run-all

# Терминал 2, из homework-03
make test-api
```

`make test-api` отключает кэш Go-тестов (`-count=1`), берёт существующие SKU
через gRPC и создаёт случайный ID пользователя. Поэтому повторный прогон не
зависит от прежнего содержимого корзин. Порты можно изменить через
`PRODUCT_GRPC_ADDR`, `PRODUCT_SERVICE_ADDR`, `CART_HTTP_ADDR` и `CART_BASE_URL`
(последняя переменная нужна только API-тестам). Для обоих сервисов значения по
умолчанию остаются `:50051` и `:8080`.

Юнит-тесты используют `testify/require`, отдельный сервис для каждого кейса и
`t.Parallel()` в тестах и подтестах. Коды gRPC-ошибок сравниваются через
`status.Code(err)`. API-тесты лежат в отдельном пакете `test/` под тегом `api`:
из кода проекта они импортируют только сгенерированный gRPC-контракт.

## Что нельзя честно измерить от этого базиса

ДЗ 2 уже содержало `RWMutex` и конкурентный тест добавления товаров. Значит,
сравнения «до мьютекса / после мьютекса» на этой ветке нет, как нет и
воспроизводимого падения старой версии под `-race`. Я не подменял историю:
добавленный race-tag тест проверяет более нагруженный сценарий и должен
оставаться зелёным. Бенчмарки измеряют текущую реализацию с `-benchmem`;
настройка и заполнение корзины в замер не входят. Один прогон на Ryzen 7 7700
дал `GetProduct` 24.64 ns/op (1 alloc/op), `AddToCart` 240.9 ns/op (4 allocs/op)
и `GetCart` 1660 ns/op (15 allocs/op). Это текущие замеры, а не выдуманное
сравнение с версией без мьютекса.
